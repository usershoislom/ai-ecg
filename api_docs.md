# ECG Annotation API — README for Frontend

dev: https://api-ecg-ai.med-uic.uz/api

prod: https://api-ecg-ai.ssv.uz/api

Base URL: `{{base_url}}/annotation`

Language: everywhere via the `lang` query parameter (`ru` / `uz`), default `ru`. If a translation is not available, the server will automatically use a fallback (ru → class code), so there will never be an empty name.



---

## Classes (superclass/subclass reference)

| Method   | Path                                                                           | Purpose                                                                                                                      |
| -------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `GET`    | `/annotation/classes/?lang=ru&type=superclass\|subclass&include_inactive=false` | List of classes. `type` is optional (without it — all). `include_inactive=true` — also return deleted (soft-deleted) classes |
| `GET`    | `/annotation/classes/{class_id}/?lang=ru`                                       | Get one class by id                                                                                                          |
| `POST`   | `/annotation/classes/?lang=ru`                                                  | Create a custom class. **Body without `code`** — it is generated by the server from `names`                                  |
| `POST`   | `/annotation/classes/{class_id}/activate/?lang=ru`                              | Restore a previously deleted class (reverse operation to DELETE below)                                                       |
| `DELETE` | `/annotation/classes/{class_id}/`                                               | Soft delete — the class disappears from lists, but old annotations with it are not broken                                    |

**Body for `POST /annotation/classes/`:**

```json
{
  "type": "superclass",           // or "subclass"
  "names": { "ru": "Name", "uz": "Nomi" },   // at least 1 language
  "parent_class_id": null          // REQUIRED (superclass uuid), if type="subclass"
}
```

The response (`201`) contains the assigned `id` and auto-generated `code` — on the frontend, `code` is not needed anywhere, only for debugging/logs.

## Annotations

| Method   | Path                                                | Purpose                                                                         |
| -------- | --------------------------------------------------- | ------------------------------------------------------------------------------- |
| `GET`    | `/annotation/?lang=ru&limit=50&offset=0&doctor_id=` | List of all active annotations, pagination + optional doctor filter             |
| `GET`    | `/annotation/study/{study_instance_uid}/?lang=ru`    | All annotations for a specific study (there may be several — different doctors) |
| `GET`    | `/annotation/{annotation_id}/?lang=ru`               | Get one annotation by id                                                        |
| `POST`   | `/annotation/?lang=ru`                              | Create an annotation                                                            |
| `PUT`    | `/annotation/{annotation_id}/?lang=ru`               | Update (full replacement of classes, not patch)                                 |
| `DELETE` | `/annotation/{annotation_id}/`                       | Soft delete                                                                     |

**Body for `POST`/`PUT` annotation:**

```json
{
  "study_instance_uid": "1.2.3...",     // required
  "series_instance_uid": "1.2.3...",     // optional
  "sop_instance_uid": "1.2.3...",         // optional
  "doctor_id": "any string",             // optional (auth is not available yet)
  "superclass_ids": ["uuid", "..."],        // MINIMUM 1 (multiple allowed, including OTHER)
  "subclass_ids": ["uuid", "..."],           // MINIMUM 1
  "other_text": null                          // free text comments from doctor
}
```

Empty `superclass_ids`/`subclass_ids` → `422` from Pydantic even before your logic.

**Response (`AnnotationOut`)** — classes are already expanded and translated:

```json
{
  "id": "uuid",
  "study_instance_uid": "...",
  "doctor_id": "...",
  "other_text": null,
  "superclasses": [{ "id": "...", "code": "MI", "name": "Myocardial infarction", ... }],
  "subclasses": [{ "id": "...", "code": "MI_ANTERIOR", "name": "Anterior MI", ... }],
  "created_at": "...", "updated_at": "..."
}
```

## Error Codes

| Code  | When                                                                                                                                                |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `422` | Basic validation failed (empty class list, invalid uuid, etc.)                                                                                      |
| `400` | Class not found / invalid type (superclass passed as subclass, etc.) / class is inactive (deleted) / `parent_class_id` not specified for a subclass |
| `404` | Annotation or class with such an id does not exist                                                                                                  |
| `500` | Internal error — send it to us, the backend has the full traceback in the logs                                                                      |

---

## Typical Frontend Flow

1. When loading the form: `GET /annotation/classes/?type=superclass` + `GET /annotation/classes/?type=subclass` → build checkboxes/tree (group subclasses by `parent_class_id`)
2. Doctor checks the boxes → `POST /annotation/` with the selected `id`s
3. When reopening an already annotated study: `GET /annotation/study/{uid}` → if there are any, show the existing ones, allow editing via `PUT`
4. "Add your own diagnosis" button → form with one field (name) → `POST /annotation/classes/`, no technical fields need to be entered by the doctor


# ECG Analysis API — README for Frontend

Input — either DICOM file upload (`multipart/form-data`, `file` field), or JSON with UIDs to retrieve data from PACS.

⚠️ **DICOM must contain a raw waveform** (`WaveformSequence`), not an image/scan. PDF/PNG scans of paper strips are not supported yet.

---

## Prediction (5 classes, with thresholds)

| Method | Path             | Input                                                                                                          |
| ------ | ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `POST` | `/predict/dicom` | `multipart/form-data`, `file` field — DICOM file                                                               |
| `POST` | `/predict/pacs`  | JSON: `{"studyInstanceUID", "seriesInstanceUID", "sopInstanceUID"}`                                            |
| `POST` | `/predict/wfdb`  | JSON: `{"record_name": "records500/00000/00001_hr"}` — internal pipeline (testing on WFDB data, not for users) |

**Response:**

```json
{
  "predictions": [
    { "label": "MI", "probability": 0.87, "threshold": 0.65, "positive": true },
    { "label": "NORM", "probability": 0.12, "threshold": 0.50, "positive": false }
  ],
  "positive_classes": ["MI"],
  "source": { "filename": "...", "fs": 500.0 }
}
```

`positive` is already calculated by the backend using a calibrated threshold (not 0.5 for all classes equally) — on the frontend, it is enough to filter by this field; there is no need to compare the threshold yourself.

---

## Prediction (original model, 150 classes, WITHOUT thresholds)

| Method | Path                    |
| ------ | ----------------------- |
| `POST` | `/predict/dicom/raw150` |
| `POST` | `/predict/pacs/raw150`  |

The same input as above. **The response is different** — no `positive`/`threshold`, only raw probabilities + top-k:

```json
{
  "predictions": [{ "label": "DIAG_042", "probability": 0.34 }, "... x150"],
  "top_k": [{ "label": "DIAG_042", "probability": 0.34 }, "... x5"],
  "source": { "filename": "...", "fs": 500.0 }
}
```

The decision about "positivity" is up to the doctor — there is no ready-made threshold.

## DICOM Metadata (not the model, just tag parsing)

| Method | Path              |
| ------ | ----------------- |
| `POST` | `/metadata/dicom` |
| `POST` | `/metadata/pacs`  |

**Response:**

```json
{
  "patient": { "PatientID": "...", "PatientSex": "M", "...": "..." },
  "study": { "StudyDate": "...", "AccessionNumber": "...", "...": "..." },
  "device": { "Manufacturer": "...", "...": "..." },
  "measurements": [
    { "name": "Ventricular Heart Rate", "code": "5.10.2.5-1", "value": 68, "unit": "heart beats per minute", "is_voltage_criterion": false },
    { "name": "RV5", "code": "RV5", "value": 1.739, "unit": "millivolt", "is_voltage_criterion": true }
  ],
  "text_annotations": ["Sinus rhythm", "Low T wave(V3,V4)"]
}
```

`is_voltage_criterion: true` — these are components of the Sokolow-Lyon criterion (LV hypertrophy), they can be highlighted separately visually. The `patient`/`study`/`device` fields are present only if the corresponding DICOM tag is populated by the device — do not rely on empty values, reliably hide in the UI anything that is not present.

## Explainability (heatmap — Grad-CAM++ × Integrated Gradients)

| Method | Path                                 | Format                                        |
| ------ | ------------------------------------ | --------------------------------------------- |
| `POST` | `/explain/dicom`                     | JSON — numerical arrays, for custom rendering |
| `POST` | `/explain/dicom/image?class_name=MI` | PNG — ready-made image                        |

Calculated **separately for each positive class** from the prediction (if the model says MI+NORM — there will be an explanation for MI and NORM separately).

**JSON response:**

```json
{
  "predictions": [...],
  "positive_classes": ["MI"],
  "nativeSignalInfo": { "fs": 1000.0, "numSamples": 12000, "note": "..." },
  "signal": [[...], "... x12"],
  "explanations": {
    "MI": {
      "grad_cam": [...],        // [numSamples] - overall importance over time (all leads together)
      "combined": [[...], "...x12"]  // [12][numSamples] - separately for each lead
    }
  },
  "source": { "filename": "...", "fs": 1000.0 }
}
```

⚠️ **Critical for correct rendering:** `signal` and all arrays in `explanations` are already aligned to the **native grid of the original DICOM** (`nativeSignalInfo.fs`/`numSamples`) — the same as the signal that you are already parsing/rendering. You can overlay `combined[lead][i]` as the background under `signal[lead][i]` 1:1 by index, no resampling of frequency/length is needed. If the record was shorter/longer than 10 seconds — sections that the model did not see (cropping/padding) are honestly `0` in the arrays.

**PNG endpoint** (`/explain/dicom/image`) — the `class_name` parameter is mandatory and must be one of `positive_classes` (otherwise `404` with the list of available ones). Ready-made image: 12 leads, heatmap overlay, physical units (mV), header with class and probability — if custom frontend rendering is not ready yet, you can temporarily just insert it as `<img>`.

A quick way to visually compare both options before integration — open `explain_preview.html` (separate file, no build required, just HTML+JS) locally in a browser.

⏱️ **Performance:** on CPU, calculation takes seconds per class (mostly Integrated Gradients) — if there are multiple positive classes, total time grows linearly. Show a loader and do not time out the request too early.

## Typical Frontend Flow

1. Open the study → `POST /predict/dicom` (or `/predict/pacs`, if the signal is already on PACS) → show classes + probabilities
2. In parallel/on request — `POST /metadata/dicom` → show demographics and device measurements in a separate block
3. Click "why?" on a specific positive class → `POST /explain/dicom/image?class_name=X` (fast path, just an image) **or** call `POST /explain/dicom` once and render it yourself for all classes at once if interactivity is needed (zoom/toggle by leads)
